Win developer and coding-agent deals with Kane CLI

A field guide for BDRs, AEs and SEs selling to engineering teams that ship with Claude Code, Cursor, Codex or Copilot. Kane CLI is the verification layer for code an agent wrote: plain-English end-to-end checks from the terminal or the agent itself, with evidence and a CI exit code. The customer-facing story for Stage 3 lives in the Kane CLI presentation. For QA-led deals, use the KaneAI play.

Overview

How to use this play

You are viewing the existing customer play: for accounts whose QA or automation team already uses TestMu, while their developers ship with coding agents and verify nothing end to end. It is an expansion into a new team, with the account manager involved from the first step.

Engineering teams now ship code written by coding agents faster than anyone can check it in a browser. Their agent can write a Playwright script, but nothing proves the feature works for a user, keeps that proof, or survives the next UI change. Kane CLI gives the developer, and the agent, a QA engineer in the terminal: describe the outcome in plain English, it drives a real browser or device, returns pass or fail with evidence, and exits with a code CI understands. Do not sell it as another test framework. Sell it as the check that makes agent-written code safe to merge.

Do not say

  • "It's free." The CLI is free to install. Runs use KaneAI credits, and new users get 10,000 credits for 30 days.
  • That mobile runs locally on any laptop. Local mobile needs an Apple Silicon Mac. Otherwise saved tests run remotely on HyperExecute macOS.
  • That it exports to Selenium or Cypress. Kane CLI exports Playwright. KaneAI web exports the other frameworks.
  • The PRISM benchmark or the "16 of 16 vs 2 of 16" result as independent. Both were run by us. Say "our benchmark".
  • That it replaces their unit and integration tests. It verifies user journeys end to end.
  • That it tests desktop apps or solves CAPTCHAs. It does neither.
  • That it works with pnpm. Use npm or Homebrew; pnpm exits silently with code 2.

Six reasons agent-written code is hard to trust

Nobody checks the browser

The agent writes the feature and unit tests pass. Whether a user can complete the flow is checked by hand, or not at all.

Review becomes the bottleneck

Agent PRs arrive faster than people can review and click through them.

Scripts break on every UI change

Agent-generated Playwright code keeps selectors, not intent. The next redesign breaks it.

Flaky CI

E2E failures nobody trusts get rerun until green, so real failures get through.

No evidence

A green tick says nothing about what was checked. Nothing is left for the reviewer or an auditor.

Developers and QA apart

Developer checks never reach the QA team's test plan, so coverage is counted twice or not at all.

Kane CLI vs the alternatives · technical view

vs Playwright MCP

MCP gives the agent a browser. Kane CLI gives it a QA engineer.

  • Intent. Kept alongside the steps, so tests heal. MCP keeps only the script.
  • Assertions. Built in, plus visual checks. MCP leaves verification to the developer.
  • Diagnosis. Suggests probable causes; MCP reports that a step failed.
  • Real-user discipline. Acts only on what a user can see, no JS injection.
  • Bifurcation. One objective branches into parallel runs for roles or data.

Playwright MCP is free and open source, and many teams already use it. Do not attack it. Position Kane CLI as what turns its browser access into a verdict and evidence.

vs the coding agent alone

The agent writes it. Kane CLI proves it keeps working.

  • State. A versioned set of tests re-run every release; the agent keeps no testing state between sessions.
  • Flakes. Detects non-deterministic tests instead of one pass or fail.
  • Coverage. Maps requirements to tests and shows gaps.
  • Triage. Groups failures and finds the root cause.

It works with the agent, not instead of it. Show the agent calling Kane CLI.

vs hand-written Playwright or Cypress

Same output, less upkeep

  • Authoring. A sentence instead of a script.
  • Upkeep. Re-authors broken steps instead of a developer fixing selectors.
  • Exit. Export any flow to Playwright code.

Our live-site test kept 16 of 16 tests passing over 11 rounds against 2 of 16 for Playwright. It is our own test, so say so.

POC plan

    

      
Day 0
Scope
Pick one repo, one staging URL, one PRD and one feature that changes in the next two weeks. Agree people and pass criteria in writing. Scope to user flows; leave unit-heavy fixtures and shared test data setup out.

      
Day 1
Install
npm install -g @testmuai/kane-cli, log in, run one objective. Install the agent skill and add a line to CLAUDE.md or AGENTS.md so the agent verifies UI changes with Kane CLI.

      
Week 1
Requirements to tests
Ingest the PRD, review the extracted use cases, design tests, and run them with testrun in parallel. Show the coverage report.

      
Week 2
Gate a real PR
Add the CI step with --headless --agent, credentials as secrets. Gate a real pull request, then make a UI change and show the heal and the evidence. Track credits used.

      
Readout
Hand back to the AE
What it caught, heals logged, CI pass rate and reruns, credits per run, open gaps with status, and the agent count.

    

    
Coach's notePOCs with large, data-heavy suites have stalled on test data and shared resources, not on Kane CLI itself. Keep the scope to flows the team checks by hand today. Log feature requests with honest status and no roadmap dates.
